# Adversarial grant estimate (v2)

> **Self-contained packaging (unofficial).** The standard documents ship in the `docs/` folder next to this file. They are the owner's files from the package dated 2026-11-12 (PERCYs v4), byte for byte. Where the owner's skill read from or wrote to a Claude Project, this copy reads a staged local copy and writes local files that it sends to the user; nothing else in the method is changed. Two things to know about the documents:
> 1. **Four ruling numbers are used more than once** across the files in `common_law_proposed/` (CL-86, CL-87 and CL-90 twice each, CL-89 three times), because separate runs numbered their rulings independently. Cite any of these as number plus file name (for example "CL-89 (2026-10-22_cascade)"), and never assume which one another agent meant.
> 2. **Some documents still speak of the Project**: `claude/...` paths, `project_info`, and a frozen `common_law.md` that is not in this package. Read `claude/<name>` as `grant_eval/_docs/<name>`; the core, index and topic files together hold the text of the frozen file.

Use when the user wants a grant (or several grant sizes) scored on their utility scale (Plan A-style US–China pause treaty = 1,000,000). This version replaces `grant-adversarial-estimate`. Changes from v1: no per-grant inputs file (the coordinator stages the standard documents once per session and subagents read local copies); a cheap structural pre-pass that fixes the facts and the no-grant world before the estimators start; a shared ledger format and simulator; a fixed prompt layout with the standard documents first; the Common Law split into an always-read core, a one-line index and topic files; a critique round only when the estimators diverge, and no rebuttal round; Proposed rulings written to one small file per run; call budgets for every agent.

## Modes: full, prepare and score

The skill runs in one of three modes. If the user names none, use **full**.

- **full**: everything below in one session, for one grant.
- **prepare** (phase one, for one grant or a batch): Setup, then Step 0 for each grant, with the pre-pass agents launched in parallel, then stop. Nothing is estimated. Setup stages the documents as usual; the simulator is not run. For each grant the coordinator saves the brief and the application under `grant_eval/_briefs/` and sends them to the user (see "Saving the brief" under Step 0) and replies with: the no-grant world in three sentences, the brief's section 12 questions ready to forward, and the FutureSearch task ids still running. Forecasts and applicants' answers take hours or days and usually move a result more than a second estimate does, so a batch is prepared first and scored later.
- **score** (phase two, one grant per session): Setup, then Steps 1 to 5 from a brief saved by an earlier prepare run. Find the newest `grant_eval/_briefs/<Org>_<date>.md`: either left by a prepare run in this working directory, or attached by the user and copied there unchanged at Setup. If there is none, run in full mode and say so. Before Step 1, write `grant_eval/_briefs/<Org>_<date>_answers.md` (one Write). It holds the applicant's or user's answers exactly as given in the prompt, each under the question it answers, and the result of every FutureSearch task listed in the brief's section 9, fetched now by task id with `futuresearch_results` in one step ("not resolved" if still empty). The grant block then names these three files under `grant_eval/_briefs/`: the brief, `..._application.md` and `..._answers.md`, which estimators and the judge read with the Read tool. Where an answer contradicts the brief, the answer wins and the agent says so. If the brief is more than about a month old, say so in the report.

## Cost model and call budgets

Measured on past runs: each model call re-reads the whole conversation so far, and the fixed part of that context (the harness's own instructions and tool list) is large, so **the cost of a run is roughly proportional to the number of model calls, not to the size of the documents**. Output tokens are the other large item. So every agent works to a call budget and the rules below. These are rules against waste, not a cap on judgment: a fact-check on a row that moves the mean by more than ~10%, or a second simulation pass after the first one shows a problem, is never skipped to stay within budget. Each agent reports two counts in its reply: **model steps** (one step = one model call, however many tool calls it issues in parallel) and tool uses. Budgets and targets are judged on steps, because steps are what drive cost; a step holding twenty parallel reads is one call, not twenty. The report's cost table shows steps and tool uses per agent next to tokens, and never calls an agent over budget on its tool-use count alone.

Rules for every subagent:
- Read all the standard documents you need in **one step**, as parallel Read calls, before doing anything else; read the brief and application in the same step or the next one.
- Read local files (brief, sources, estimates, ledgers, critiques) as **parallel Read calls in one step**, one per file. Never join several files into one shell `cat`: a large tool output is saved to a file and only its start is shown, which forces a second round of reads and roughly doubles the tokens spent on those files.
- Keep every tool output small. Make searches specific (a full-text search on a common word returns tens of kilobytes); prefer a lookup by id or exact name. If an output is cut off and saved to a file, read only the part you need from that file rather than rerunning the command.
- **Never re-read a file that is already in your context.** If you need a number from a document you have read, find it in your context.
- Do web research in batches: several searches in one step, then several fetches in one step.
- Write each output file **once**, complete, with a single Write call; do not build it up over many Edit calls.
- Run `simulate.py` on your ledger at most three times (first run, one revision, one final check). Fix several rows per revision, not one per run.
- Do not narrate between tool calls; a step that only contains commentary is a wasted call.
- **Never poll in a loop.** A tool that returns "still running" gets at most three further checks, spaced out; after that use whatever partial result is available, say so, and move on.

Targets (model steps): pre-pass ~12 for a listing-only grant and ~20 for a Commons grant with transcripts; each estimator ~8; each critique ~3; judge ~8; coordinator ~30 for the whole run. Tool uses will be several times higher, mostly from the parallel reads of the standard documents (about 20 as of November 2026); that is expected and not an overrun. An agent that expects to exceed its step target by half says why in its reply.

Rules for the coordinator: **launch every subagent in the foreground (`run_in_background: false`)**, including the pre-pass, both estimators, critiques and the judge. Each result then arrives in the step that needs it, which keeps the run in one turn. Foreground agents launched in the same step still run in parallel. Issue parallel tool calls wherever steps are independent (the staging copy in one Bash call, both estimators in one step, both critiques in one step, the verification checks in one Bash call); do not re-read staged files; one grant per session in full and score modes (prepare mode may take a batch), since a longer conversation makes every later call dearer.

## External tools: FutureSearch, GitHub and Manifund

**FutureSearch.** FutureSearch is an AI superforecaster. The human user has found it less skilled than frontier models at everything except explicit, traditional probabilistic forecasts of simple future events, and it is slow and expensive, so use it only for a question of that kind that is central to the calculation. It expects much slower AI progress than the grantmakers this system serves; on a question whose answer depends on the speed of AI progress, side with the grantmakers and say that you adjusted. Every report lists the queries made and their results. If the session has no FutureSearch tools, skip FutureSearch entirely: record each question in the brief as "FutureSearch not connected" and say so in the report. **Submit early, read late, and measure time with the clock.** Agents cannot feel elapsed time: a burst of status checks a few seconds apart feels like "several minutes" but isn't, and even a low-effort task can take ten minutes or more. So:
- The pre-pass submits all its questions in one step at the start, runs `date -u` in the same step, and records each task id, session id and the UTC submission time in brief section 9. It never calls `futuresearch_status` or `futuresearch_progress` and never waits for results; it makes at most one `futuresearch_results` attempt, as its last action before writing the brief.
- The coordinator reads results as late as they can still change the verdict: one `futuresearch_results` call per pending task immediately before launching the estimators (pass any results in the grant block), and, for any task still empty, one more immediately before launching the judge (pass them to the judge, which prices them against the brief's assumptions and says what changed). Before that last fetch, run `date -u`; if less than about 20 minutes have passed since submission, wait first with a single Bash `sleep` of at most 600 seconds. Never infer elapsed time from how many calls have happened.
- A task still empty after that is recorded in the report as "not resolved in time" with its task id, so a later session can fetch it. Status widgets may never show "completed" even when results exist, so always use the results call rather than status. Never fetch a FutureSearch download link with `curl` or `WebFetch`; `futuresearch_results` is the only route. Never spend more than about six calls in total on FutureSearch.

**GitHub.** The GitHub API is often blocked from the sandbox; do not retry it or work around it. Use, in this order: (1) `git ls-remote --heads --tags <repo url>` for the branch list, and `git clone --bare --filter=blob:none` (or a shallow clone) when commit dates are needed, since plain git over HTTPS works; (2) `WebFetch` of the organisation's GitHub page (`github.com/<org>?tab=repositories`) to list **every repository in the organisation**, not only the one the application names, because side repositories (a hiring take-home, a tooling repo) are evidence about activity; (3) `WebFetch` of a repository's commits page for the latest commit date on each branch. Report the date of the latest commit on any branch of any repo in the org.

**Manifund.** `WebFetch` returns only a model-written summary of a Manifund page, so never scrape a listing by hand. `fetch_manifund.py` (staged at Setup as `grant_eval/_docs/fetch_manifund.py`) reads the listing as data. `python3 grant_eval/_docs/fetch_manifund.py <listing URL or slug> --out grant_eval/<org>/source/` writes `application.md` (the full application text, goal and minimum, amount raised, every donation with date and donor, open offers), `comments.md` (the whole thread with authors and dates) and `listing.json`, and prints a short summary. If only the organisation's name is known, `--find "<title words>"` lists matching listings with their URLs. The pre-pass runs it as its first step for any Manifund listing, once. If it fails, say so in the brief and fall back to `curl` of the page; if the sandbox refuses that too, stop and ask the user to attach the application. Never guess a listing's contents. Donations made outside Manifund do not appear in it.

2. If the user keeps files from earlier runs, copy them in now, unchanged: Proposed-ruling files into `grant_eval/_docs/common_law_proposed/`, their own `milestones_added.md` over the staged copy, and saved briefs into `grant_eval/_briefs/`.
3. Verify with one Bash call and paste its output into the run log: `python3 "<skill base directory>/check_staging.py" "<skill base directory>/docs" grant_eval/_docs`. It checks that every bundled file was copied byte for byte, that each of CL-1 to CL-83 and CL-91 has exactly one full text across the core and topic files, that the index has its 84 lines, and that `simulate.py --template`, `simulate.py` on the template, `mean_range.py` and `fetch_manifund.py --help` all run. **Never correct, tidy or "fix typos" in a staged copy, and never delegate the staging to a subagent.** Subagents never edit the staged copies and never rebuild them. Grant-specific material (the application, Commons documents) is still read by the pre-pass from its source.

## Independence

Estimators A and B must not read each other's files, transcripts or replies before the critique round, and no subagent reads another subagent's transcript at any point: the only shared inputs are the standard documents, `brief.md`, and `grant_eval/<org>/source/`. Under `grant_eval/`, a subagent reads only the standard documents named in its prompt and its own grant's folder: it never opens a past report (any file with `grant_forecast` in its name), another organisation's folder or anything under `grant_eval/_ledgers/`, opens files under `grant_eval/_briefs/` only when its prompt names them (score mode), never searches `grant_eval/` as a whole (the results would quote past reports), and never writes under `grant_eval/_docs/`. Every subagent prompt states this. An estimator that discovers another agent's reasoning by accident says so in its reply.

## Prompt layout for every subagent

Write each subagent prompt in this fixed order, so the shared part is identical across agents and runs:

1. **Standard documents block** (identical text every time): the always-read list and the topic-file list above as local paths under `grant_eval/_docs/`, the names of the current files in `grant_eval/_docs/common_law_proposed/`, the instruction to read the always-read files in one step with the Read tool and to reply `MISSING DOCUMENT` and stop if one is not there, the packaging note's two points (duplicate ruling numbers; Project paths in the documents mean the staged folder), the local paths of the staged simulator and template, the call-budget rules and the agent's target, the external-tools rules, the independence rule, and the one-paragraph description of the ledger CSV and `simulate.py` usage.
2. **Role block**: pre-pass / estimator / critic / judge instructions (below).
3. **Grant block**: the organisation, grant sizes, the grant's source class (Commons with transcripts and evaluator material, or listing-only), which topic files apply (the pre-pass recommends them; method-and-programs always), the path to `grant_eval/<org>/brief.md` (in score mode, the three files under `grant_eval/_briefs/` instead), and (for the pre-pass only) where the raw material is.

Keep all working files in `grant_eval/<org>/` in the working directory.

## Ledger format and simulation

Every estimate and the judge's verdict carry a ledger CSV in the `ledger_template.csv` format (one row per consequence, with `size`, `kind`, `weight`/`p1`/`p0` for events, `ev`/`sigma` for continuous and charge rows, `pivotal`, `exec`, `exec_mode`, `group`, `branch`/`branch_val`, `post2030`). Agents do not write their own Monte Carlo code. They run:

```
python3 grant_eval/_docs/simulate.py <X>_ledger.csv --branches '{...}' --corr '{...}' --exec '{...}'
```

and paste the output into their report. The analytic mean is the headline; quantiles are descriptive (CL-16). Values questions (CL-11) are `branch` columns with their weights in `--branches` (CL-74 corners and fixed-weight spread come out automatically). The correlated execution factor goes in `--exec` and applies only to program rows, never charges (CL-37, CL-40).

Every estimate states, in one line near the top, the exact `--branches`, `--corr` and `--exec` arguments it used, so the coordinator and judge can rerun it and feed `--diff`.

Two columns matter for comparability and are mandatory:
- **`group`**: every row carries one of the fixed categories defined in `simulate.py --help`. **File by the causal path, not by sign or branch**: a harm-branch mirror of a positive row takes the same group as that row (a "harness is net capabilities" row goes in `uptake` with "harness is used"; a "retrospective normalises automated R&D" row goes wherever the retrospective's positive row went). `values` is only for rows that exist in no causal path (pure signalling or trust-norm rows); `exposure` is only for press, scandal, partisan-coding and incident rows. Independent estimators never share row names, so `--diff` and the agreement test compare group totals.
- **`exec_mode`** on event rows with an execution factor: `credit` whenever the row's p1 − p0 is the grant's own increment, including the common case of a small increment on a base rate from other causes (the increment scales with execution; see Proposed CL-92); `p1` only when p1 is entirely the outcome of the team's own work, since `p1` mode multiplies the whole with-grant probability, base rate included, by the execution factor and turns small increments on a base rate negative. State the choice once in the estimate; it changes the mean.

An overlap row that corrects program rows carries the same `exec` group and `branch` as the rows it corrects; the "never multiply charges" rule applies to money, people and exposure charges.

`simulate.py --diff A.csv B.csv --size <s> --branches-a '{...}' --exec-a '{...}' --branches-b '{...}' --exec-b '{...}'` prints each ledger's headline mean under its own weights and factor, the group-total comparison the agreement test uses, then row-level differences by name. Always pass both ledgers' own settings; without them the diff compares raw EVs and misleads.

- Grant sizes to score. By default the sizes are the cumulative end points of the tranches in the brief's section 1 (usually four to six), plus any size the user names. Use $250K / $1M / $3M only when no tranches can be identified.
- Optional facts from the applicant: spending by year, what each grant size buys, c3 vs c4.

## Step 0 — Structural pre-pass (one `sonnet` agent)
Start one Agent subagent (general-purpose, model `sonnet`) before the estimators. It is the only agent that reads the raw Commons material in full, and the only one that runs web searches for funding facts and FutureSearch. Its job is the structure of the grant, not its value: it never estimates utility. It always runs, but its scope depends on the source class:
- **Commons grant** (transcripts, evaluator notes, comment threads): all twelve sections below; target ~30 calls.
- **Listing-only grant** (an application page and nothing else, e.g. grantmaking.ai): sections 1, 2, 3, 7, 8, 9, 10, 11 and 12 only, with section 2 reduced to what is public; skip the evaluator table and quotes unless such material exists; target ~15 calls. The web checks and FutureSearch are kept, because they are what the estimators would otherwise each do separately and differently.

Role block for the pre-pass:
- Read the always-read documents and the index from `grant_eval/_docs/` in one step, then all raw material for this grant: the application, interview transcripts, evaluator notes and comment threads, shared notes. Submit the FutureSearch questions early, in the same step as the first web searches, so they run while you read; follow the FutureSearch and GitHub rules above.
- Write `grant_eval/<org>/brief.md` with these sections, each short and sourced (document name and location for Commons material; URL for the web):
  1. **The organisation and the ask.** What it does, team size and seniority, and the plan year. Then a **tranche table**: what each successive block of money buys, in the organisation's own priority order, from the first dollar up to the top of the ask (or to the point where further money would only be banked, as a final tranche). One row per tranche: what it buys, its cost, the cumulative size at which it ends, and whether the applicant stated it or you inferred it from the budget. Use the organisation's natural units (keep the current team, each hire, each cohort or campaign, banked runway); four to six tranches is typical. Do not value them.
  2. **Funding facts.** Cash and runway, revenue, latest Form 990 figures (revenue, expenses, net assets), grants from each major funder by year with sources, grants pending or intended elsewhere, matching pledges, debts to the platform or evaluators, and any earlier award from the same platform. Flag anything an AI-written evaluation asserts without a source.
  3. **The no-grant world under CL-8, CL-62 and CL-91.** Money that stays in both worlds, and what the organisation does without the grant. Then a funder table for CL-91, one row per outside funder or donor group that matters: its tier and price from the CL-91 table (say so when you assigned an unlisted funder to the nearest tier), what it is expected to give without the grant and with it at each grant size (probability and amount, with the reason for any difference: a smaller ask, a skipped application, a rescue), and so the expected dollars displaced. Model each funder's real response; do not force equal probabilities in the two worlds. Include the organisation's own later fundraising that banked money would reduce.
  4. **Absorptive capacity.** The applicant's own statements about hiring rate and bottlenecks, quoted verbatim; the share of each grant size that can be spent in the plan year under CL-35, and what the rest becomes.
  5. **Evaluator views (CL-12).** A table: evaluator, position or rank, amount they fund to, conflict of interest, one-line view. Mark AI-written evaluations as such.
  6. **Verbatim quotes that matter.** Up to 15 short quotes from transcripts or notes that an estimator would otherwise need the full transcript to find (hiring caps, minimum sizes, what they would cut first, admissions of risk).
  7. **Facts checked on the web.** Each with a source. Include track-record items (past outputs, press, audits of reach claims under CL-30) and, for code projects, every repository in the organisation with its latest commit date.
  8. **Values questions (CL-11).** The contested values questions this grant raises, stated neutrally, with the rows each one would affect. Do not pick an answer.
  9. **FutureSearch.** At most four forecast questions (at most two for a listing-only grant), chosen for what moves the structure: the main other funder's next award (P and size), one key base rate the ledger will need, and nothing the estimators could settle by reading. Record each question with its task id, session id and UTC submission time, and its result if your single end-of-pass results attempt returned one; otherwise mark it "pending" (the coordinator fetches it later).
  10. **Open gaps.** Facts you could not establish, for the estimators to treat as uncertain and the report to list as open questions.
  11. **Topic files and rulings likely to apply.** Which `common_law_topics` files this grant needs, and the index lines of the rulings most likely to matter.
  12. **Questions for the applicant or grantmaker.** Up to six questions, most valuable first, that only the applicant or the grantmaker can answer and that would move the result most. Start from sections 1, 3, 4 and 10: what the organisation would do with the first block of money and with each block after it, in priority order with costs (ask this whenever the tranche table is inferred); current cash, burn and runway; applications pending or planned elsewhere, and whether a grant here would shrink them; named hires versus open posts; audience-composition or outcome data. Word each so that it can be forwarded as written, and say in a few words how much the answer matters.
- Save the application text (and any Commons document an estimator is likely to need in full) as files under `grant_eval/<org>/source/`, so the estimators can read them locally.
- Keep the brief under about 3,000 words (about 1,500 for a listing-only grant). Quotes count toward that; prose does not need to.
- Reply with the no-grant world in three sentences, the absorptive-capacity shares by size, the topic files recommended, and your call count.

The coordinator reads the brief before continuing. If section 3 or 4 is missing something the user can answer, ask once now rather than letting the estimators guess.

**Saving the brief.** In every mode the coordinator copies `brief.md` unchanged to `grant_eval/_briefs/<Org>_<date>.md` and sends that file to the user, so that the facts a forecast rested on outlive the session. In prepare mode it also copies the application text from `source/` to `grant_eval/_briefs/<Org>_<date>_application.md` and sends it, because the score run starts from these two files; tell the user to attach both when they start the score run in a new session. In prepare mode the pre-pass follows the same FutureSearch rule (submit at the start, record ids and time, one results attempt at the end); the score run fetches the results.

## Step 1 — Two independent estimates (run in parallel)
Start two Agent subagents (general-purpose), Estimator A with model `opus`, Estimator B with model `fable`, with identical prompts in the layout above, launched in the same step. Neither sees the other. Both get `brief.md` and the application from `grant_eval/<org>/source/`; they do not get the transcripts or evaluator notes pre-loaded. If an estimator needs a Commons document the pre-pass did not save, it asks the coordinator (in its reply) rather than failing silently; the coordinator fetches it and continues the agent.

Role block for estimators:
- Work independently; don't look for other forecasts of this grant and don't read any other agent's files or transcript. Read the always-read documents, the topic files named in the grant block, `brief.md` and the application in one step. Use the index to find any other ruling you need and fetch its full text from its topic file before citing it. Take the brief's funding facts, no-grant world, absorptive-capacity shares and FutureSearch results as given; if you think one is wrong, say so in a flagged line and price it the brief's way for the headline, your way as a sensitivity. Web search is for facts about the ledger rows, not for facts the brief already settles.
- Question: expected utility of each grant size vs. not making the grant, at the listed weights, following the Common Law (especially CL-1 to CL-10). Cite rulings by number where you apply them. The grading standard is how a top AI model in 2030 would estimate the grant's utility (CL-1, CL-7). Give the true expected value as best you can; do not try to predict a particular evaluator's quirks. The ledger is an expected-value calculation over the milestones and others like them, but you may invent milestones, priced by common-sense comparison with listed ones, and adjust for subjective and intuitive factors where you say so.
- Required steps: (1) what each tranche in the brief's tranche table buys; the sizes you score are the cumulative end points of those tranches plus any size the user named, all in one ledger built from the same inputs, so that the difference between two consecutive sizes is the value of the tranche between them; (2) org-level ledger for the org's whole next-year program (outcome | type per CL-5 | weight | P with the program | P without | contribution, plus the fraction attributable to next year's spending), scaled to each grant with an explicit marginal-vs-average factor; charges for follow-on resources (CL-4, at the supplying funder's CL-91 price), overlap, and downside as separate signed lines; funging under CL-91 as rows whose names begin `Funging:` and that sit in the `money` group, built from the brief's funder table: first cap total displacement at 75% of the grant, then one negative row for the programme value lost because the displaced dollars are not net new to the organisation, and one positive row per funder tier crediting displaced dollars at that tier's price × 0.8. Write every other row as if all grant dollars were net new, so that the ledger's mean is the with-funging headline and the mean minus the `Funging:` rows is the base value; report both at every size; (3) scale-up and track-record checks (CL-9, CL-15; for a team with no budget beyond the grant, compare instead with the researcher-year band and the nearest large organisation's historical rate as a CL-6 upper bound); (4) the grant ledger as `<X>_ledger.csv` in the template format with `group` filled on every row per the filing rule and `exec_mode` stated for event rows, run through `simulate.py`, with the output and the exact arguments pasted in (mean, median, P10/P90, P(negative), post-2030 share per CL-18); (5) every values question from the brief's section 8 priced both ways as a `branch` (CL-11), plus any you add; (6) any situation the Common Law doesn't cover, with the call you made, and any ruling you disagree with, with the affected rows recomputed. Small research outputs get no separate first-run or "toy" quality factor on top of the execution factor (CL-37: no second dispersion on the same thing); CL-19's quality factor is for venue programmes.
- Output: `<X>_estimate.md` with the ledger tables and one line of reasoning per row (every row gets its line; keep narrative outside the tables short), plus `<X>_ledger.csv`, each written once; reply with the summary table (mean, median, P10, P90, P(negative), per $1M, % post-2030), the `simulate.py` arguments, the names of your three largest rows at $1M, and your call count.

## Step 2 — Decide whether a critique round is needed
The coordinator runs `simulate.py --diff A_ledger.csv B_ledger.csv --size <smallest common size>` **with each estimator's own `--branches-a/--exec-a` and `--branches-b/--exec-b`** (from their replies) and reads the output. The estimates **agree** when all of these hold at the $1M size (or the smallest size scored): the headline means are within 30% of the larger one's absolute value, or both are within 50 utility of zero (the diff prints this); the largest group is the same in both (the diff prints this); and no group total differs by more than 30% of the larger mean (the diff prints the count). Row names are not compared. If the only flagged groups look like filing differences (the same causal path in different groups), note that in the report but still run the critique; the filing rule exists to make this rare.

- **Agree:** skip to Step 3 with no critiques. Record in the report that the critique round was skipped and why.
- **Diverge:** continue both estimators with SendMessage in the same step. Each reads the other's estimate and ledger, runs `simulate.py --diff` with both settings, and writes `<X>_critique_of_<Y>.md` in one Write: the groups and rows that move the $1M mean most, what the other assumed, why it's wrong, what number to use instead, any misapplied Common Law ruling, then a one-line list of any smaller disagreements, plus anything the other did better. No self-revision and no rebuttal: the judge weighs the critiques against the estimates directly.

## Step 3 — One neutral judge
Start one fresh `fable` judge that made no estimate, with the same prompt layout. Point it at `brief.md`, both estimates and ledgers, and the critiques if any were written, with this role block:
- You made no estimate. Read the standard documents, the brief, both estimates, both ledgers and any critiques in one step. Run `simulate.py --diff` on the two ledgers with each estimator's own settings and identify every remaining difference, by group and then by row, that moves the $1M mean by more than ~10% (include the marginal-vs-average factor and the post-2030 discount). Where critiques exist, treat each critique as the strongest case against that estimate; where none exist, the estimates agree and your job is mainly to check them against the brief and the Common Law.
- Decide each difference: A's value, B's value, or your own, with one line of reasoning; judge evidence, not confidence, length or tone; no default midpoints. Apply the Common Law where it speaks to the dispute and cite the ruling (fetch full text from the topic file before citing). If you land outside the range of the two estimates, say so and show both alternatives.
- Web-check any factual claim that moves the result >10% and is not already sourced in the brief; batch the checks.
- Compare your P10–P90 with the spread of comparable outcomes; if yours is much narrower, justify it or widen it.
- Funging (CL-91). Check both estimators' `Funging:` rows against the brief's funder table: the tiers, the 75% cap, the 0.8 factor on credits (not on CL-4 charges), and that no other row already nets out displaced money. Your own ledger follows the same layout; report the with-funging mean (the headline) and the base value at every size.
- Tranches. Score every cumulative tranche end point in your one ledger, from the same inputs; never take a difference between numbers from different ledgers. A tranche's value is the mean at its end point minus the mean at the previous end point (the first tranche is measured from zero). Value per dollar should fall from one tranche to the next; where it rises, either name the real threshold that explains it (a minimum viable size, a full-time hire) or correct the ledger. Write `tranches.csv` with the columns `org,date,tranche,what_it_buys,cost_usd,ends_at_usd,value_with_funging,value_base,per_1M_with_funging,source,note`, where `source` is `applicant` or `inferred`.
- Write `judge_ledger.csv` (with `group` on every row), run `simulate.py` for all sizes, and give mean, median, P10/P90, P(negative), the share of value from post-2030 effects, and up to 4 open questions only the grantmaker or applicant can answer (start from the brief's section 10).
- Candidate rulings: for each judgment call you think the Common Law should cover, first search `common_law_index.md` and the proposed folder for a ruling that already does; if one does, cite it instead. List as candidates only calls that no ruling covers, that moved a headline mean by more than ~10%, and that another grant could plausibly raise. At most three.
- Range on the mean. P10 to P90 from `simulate.py` is outcome risk: how the world might turn out if the ledger's inputs are right. Also report how far the mean could move if the inputs are wrong. Pick the three to five inputs whose uncertainty moves the mean most; always consider the no-grant run-rate and in-year share from the brief, the marginal-vs-average factor, and the largest row's headcount, rate or probability shift. For each, state a plausible low and a plausible high value (roughly its 10th and 90th percentile) and the mean at the smallest size scored with only that input changed. These means may be computed by scaling the affected rows and do not count toward the `simulate.py` run limit. Then run `python3 grant_eval/_docs/mean_range.py --central <mean> --low <m1,m2,...> --high <m1,m2,...> --names "<n1,n2,...>"` and paste its output.
- Candidate milestones and parameters: list every price or recurring factual parameter your ledger uses that is not on the Milestones documents and that another grant could plausibly use, in the entry format given in Step 4, having first checked the Proposed section for an entry that already covers it. Separately list every values weight (CL-11) and post-2030 discount you chose yourself; those are not proposed as entries.
- Write `judge_verdict.md` once, with the ledger tables and one line per decision; keep narrative short. Reply with summary table, the range on the mean, the three decisions that mattered most, open questions, candidate rulings, candidate milestones and parameters, the values weights and discounts you chose, sources, the `simulate.py` arguments, and your call count.
